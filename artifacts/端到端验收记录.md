## C. AC-7 的实测发现（含一次自我纠错，务必看完）

### C.1 第一版结论是错的

本轮第一次跑 AC-7 压测时记下的是「串行 7.71s → 并发4 2.49s，比值 0.323」。
那个数字**不可信，已作废**。原因是压测把同一批 45 篇先串行跑一遍、再并发跑一遍，第二遍命中了
`_stage_engine1` 的「`engine1_text` 已落库就复用」分支——并发轮只打了 112 次引擎调用，串行轮打了 224 次。
**量到的是缓存命中，不是并发收益。** 结构化计数器（在飞峰值/调用总数）一加上来，两轮 224 vs 112
立刻暴露，这也是为什么门禁必须同时带结构断言。

### C.2 同量冷跑的真实数字（两组各 45 篇、张数同分布）

| 并发度 | 墙钟 | 与串行比值 | 加速 | 引擎调用 | 在飞峰值 |
|---|---|---|---|---|---|
| 1 | 7.71 s | 1.000 | 1.00× | 224 | 1 |
| 2 | 4.31 s | 0.559 | 1.79× | 224 | 2 |
| 4 | 3.79 s | 0.492 | **2.03×** | 224 | 3 |
| 8 | 3.92 s | 0.508 | 1.97× | 224 | 4 |

pytest 里连跑三次（并发1 vs 并发4）：比值 0.479 / 0.509 / 0.487。

### C.3 三条结论

1. **PRD 原文的「≤25%」不可达**：那是 4 消费者的理论下限，等于要求零开销的线性加速。
   第一版修订写成 35% 也不对（用的就是 C.1 那个坏数字），现在 PRD 已改成
   「**结构化判据为主 + 墙钟 ≤60% 为辅**」，见 PRD §9.1 与 §12 Q16。
2. **收益在并发 4 附近饱和，加到 8 没有增益**：每篇要开独立 DB session 并多次 commit，
   这些写在 SQLite 的单写锁（WAL 也只允许一个写事务）上排队。瓶颈已经从「等引擎」
   变成「等写锁」——**再加并发度不会更快，要快得先减少每篇的提交次数**。
3. **mock 会放大 DB 占比**：真实引擎的单张耗时是秒级网络等待，远大于 122 ms 的 DB 开销，
   所以真实加速大概率高于 2×。这也是为什么「45 篇 ≤5 分钟」只能由 AC-10 真机计时判定，
   mock 断言替代不了它（本轮真实冒烟仍未跑，见 D）。

### C.4 门禁怎么改的（不是放宽，是换了正确的量法）

`backend/tests/test_v12_concurrency.py::test_class_of_45_runs_in_parallel_without_mixing_up`：

* 一次造 90 篇（两组各 45 篇、同分布），**串行用第一组、并发用第二组**，两轮都是冷跑；
* 断言两轮引擎调用次数相等（=224）——不同负载之间的墙钟比值没有意义；
* 断言在飞峰值：串行 = 1，并发4 满足 `1 < peak ≤ 4`。**不钉 peak == 4**：篇与篇的
  「引擎等待 / DB 写入」相位会错开，实测峰值常在 3，那是采样相位而不是并发失效；
  钉 ==4 会让门禁自己变红（本会话实测出现过 peak=3 的冷跑）。
* 墙钟阈值 0.60：实测带宽 0.48~0.51，退回串行是 ~1.0，这条既能抓大倒退又不误报。

**既有断言一条没删、没放宽**；这次改动是把一个「测错了的量」换成「测对了的量」。

## E. 本轮改出来的两个真实缺陷（不是测试适配）

1. `deploy/backup.py::verify_backup` 原来只捕 `BackupError/OSError/tarfile.TarError`。截断的

   依赖单向、不成环。已收敛为模板侧转发到 config，改兜底文案只剩一处。

顺带钉住一条容易踩的约束：`PATCH /api/essays/{id}` 的 `final_text` 为空一律 400，
**这个端点不能只改标题**（`test_patch_requires_non_empty_final_text`）。若以后要支持"只改标题"，

## H. 二次审计发现 2：OPT-01 的「句级跳转」没做（已补）

PRD §03 OPT-01 的承诺是两件事：① 对照面板默认展开（第一轮已做）② **按句切分存疑处**。

实现口径（`components/DiffText.tsx`）：

1. `splitSentences()` 按中文句末标点（。！？；… + 半角对应）断句，标点与其后的右引号
   归前一句；无标点/空串/纯空白都只出一格，`insert` 候选为空时仍保留可点的占位格。
2. key 规则 `seq:index[:part]`：**只有一句时不带句序号**，所以既有断言（`"1:1"`/`"2:0"`、
   「存疑 2 处」）一字未改就继续成立；多句才追加 `:1`、`:2`。
3. 渲染与「存疑清点」共用同一个 `listSuspectKeys`，因此计数、点看状态、定稿前提醒三者
   天然同口径——不会出现「面板说 2 处、提醒说 1 处」。
4. 不改数据模型：`diff_json` 仍是引擎给出的段落序列，切分只发生在展示层（PRD 原话）。

新增 7 例：`DiffText.test.tsx` 6 例（断句/右引号归属/无标点/尾随空白/一句多 key/逐句可点），
`ProofreadPage.test.tsx` 1 例——**一段两句的稿子必须点两次才算核对完**，这条最能钉住

## K. rev.3 补做的两项实测（PRD 里标着「需复测 / 只能真机」的开放项）

### K.1 45 篇整册 PDF 导出计时（新增 `deploy/bench_export.py`）

PRD §02 一直挂着「三套模板整册 PDF 28.0s；**45 篇规模需复测**」，FR-03 也把它列为验收口径。
这一项**不需要调引擎**（成册只读库里的定稿文本 + Playwright 渲染），所以能在本机自证，不必等老师。

做法：隔离数据目录 → 45 名学生 / 1 期 / 45 篇全部 `proofread`（正文用合成句池，400~1200 字、
3~6 段，与真实稿件同量级）→ 起 uvicorn（`EWB_WORKER_ENABLED=false`）→ 走真实 HTTP 端点计时。

```
[bench] 45 篇全部定稿，issue=1，开始逐套模板计时
[bench] OK  elegant  HTTP 200    2.90s   0.22 MB -> bench-elegant.pdf
[bench] OK  formal   HTTP 200    2.04s   0.20 MB -> bench-formal.pdf
[bench] OK  playful  HTTP 200    2.99s   0.36 MB -> bench-playful.pdf
[bench] OK  single   HTTP 200    2.43s      79 KB
```

用 PyMuPDF 复核产物不是「空壳快」：`elegant` 49 页、`formal`/`playful` 各 50 页，
三套里 **45 个学生名全部出现**，标题取自 FR-11 的 `title` 字段（无「未命名」泄漏）。

结论：

- 「全部定稿 → 导出 ≤ 1 分钟」在 45 篇规模下**达成且余量约 7 倍**（三套合计约 8s）。
- T05 记的 28.0s（5 篇）与本轮 8s（45 篇）不矛盾：T05 三次分别是 13.65s / 9.79s / 4.57s，
  递减说明大头是**首帧 Chromium 冷启动 + 当时机器负载**（那轮刚跑完真实 OCR），规模不是瓶颈。
- 脚本以 `--limit-seconds`（默认 60）作退出码，可直接当门禁；`--keep` 保留 PDF 供目视。

**过程里踩的坑（记下来）**：脚本第一版跑出来三套全 `FAIL HTTP 404`。根因不是导出链路，
是**压测脚本自己漏了 `await session.commit()`**——45 篇压根没落库，服务端如实返回「期数不存在」。
这恰好从反面验证了 `_load_essays` 与 404 分支是对的，也再次说明：**取证脚本必须自带负对照**，
否则「测过了」只是「跑过了」。

### K.2 Linux 下归档 0600 落盘位（AC-8 剩下的半程）

`test_backup.py::test_archive_is_owner_only` 在 Windows 上按 POSIX 语义跳过，此前只能断言到
系统调用层（`os.open`/`os.chmod` 收到 0600）。本轮用 WSL2 Ubuntu 在真实 POSIX 文件系统上补测：

```
Linux 6.6.114.1-microsoft-standard-WSL2   /tmp -> tmpfs
backup: OK /tmp/tmp.../out/ewb-backup-20260912-040136.tar.gz
mode=600            <- 归档落盘位
umask=0o22          <- 进程掩码更宽，说明 600 是显式 chmod 的结果，不是继承来的
verify: OK          <- 归档能还原出可读 SQLite
tar 成员 6 个，全部相对路径（essay.db / manifest.json / config/ / config/engines.yaml / photos/ ...）
负对照：同目录另建文件 chmod 644 -> mode=644，与归档的 600 不同，文件系统确实按位区分
```

顺带观察到一条既有防护在起作用：归档输出目录被刻意放在数据目录**内**时，脚本打印
「输出目录位于数据目录内，跳过清理」并拒绝参与后续 prune——避免把备份自己扫掉。

因此 AC-8 从「达成（Windows 权限位除外）」升级为「**达成，含 Linux 落盘位实测**」；
生产机上线时仍建议 `ls -l /var/backups/essay-workbench/` 再确认一次（文件系统与 umask 可能不同）。
